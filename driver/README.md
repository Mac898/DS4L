# driver/

A fork of the in-kernel `hid-playstation` driver with one change
(`ds4l.patch`).

When userspace puts a DualSense into audio mode (the `0x36` output report),
the controller interleaves microphone data into its `0x31` input reports.
The stock driver reads those as gamepad state, giving random axes and
buttons (the mouse flies around under Steam Input). The patch drops those
reports in `dualsense_parse_report()`. Everything else still works through
the kernel: gamepad, touchpad, sensors, battery, LEDs, rumble, and the
hidraw node DS4L uses for audio.

Audio input reports have bit 1 of `data[1]` set; gamepad reports don't.
The patch also adds a `ds5_drop_all_input` module parameter that drops every
input report. DS4L uses its presence to tell this module from the stock one.

The generated `hid-playstation.c` is derived from the kernel driver and is
GPL-2.0-or-later. The scripts here are glue.

## Files

* `ds4l.patch`: the change, against `drivers/hid/hid-playstation.c`.
* `prepare.sh`: copies the base file and `hid-ids.h` from a kernel source
  tree and applies the patch. Run it to rebase onto a new kernel.
* `hid-playstation.c`, `hid-ids.h`: generated by `prepare.sh` and committed,
  because kernel-headers packages ship neither.
* `Makefile`: out-of-tree build.
* `dkms.conf`, `install-dkms.sh`: install into `updates/dkms`, which
  overrides the stock module and is rebuilt on kernel updates.
* `load.sh`, `load-debug.sh`, `unload.sh`: swap modules without installing.

## Build and try

```sh
./prepare.sh        # needs a kernel source tree
make
sudo ./load.sh      # unplug or detach the pad first
sudo ./unload.sh    # back to stock
```

## Install

```sh
sudo ./install-dkms.sh
sudo modprobe -r hid_playstation && sudo modprobe hid_playstation
cat /sys/module/hid_playstation/parameters/ds5_drop_all_input   # exists = DS4L
```

The daemon does this itself on first run unless started with `--no-auto-dkms`.

## How the audio flag was found

Load with `sudo ./load-debug.sh`, which drops every input report so nothing
can reach the input layer. Stream audio from userspace and read the raw
reports from hidraw (`tools/bt_gap_probe.py` or `hexdump`) with the mic
muted and unmuted. Audio reports have bit 1 of `data[1]` set; gamepad
reports have bit 0.

Checked on hardware with audio mode on: 700 audio reports, none missed, no
false hits, against 4757 gamepad reports. With the patch loaded and audio
streaming, the gamepad device saw no spurious events over a 6 s capture,
while hidraw showed both report kinds (4095 gamepad, 601 audio). Stick
movement and the touchpad worked normally.
